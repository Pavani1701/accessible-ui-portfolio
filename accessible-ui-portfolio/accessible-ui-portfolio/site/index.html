Accessible UI Portfolio

A small design system and citizen-facing application flow, built to WCAG 2.1 AA and Section 508 with semantic HTML5, Sass and dependency-free JavaScript.

Explore the work

  • Component library

    Buttons, alerts, accordion, tabs, modal dialog and a sortable, filterable data table. Each follows the WAI-ARIA Authoring Practices keyboard model.

  • Multi-step application form

    Inline validation, an error summary that receives focus, accessible date input, focus management between steps, and a review-and-change step.

  • Source code and tests

    Sass architecture with design tokens, plus automated axe-core accessibility and keyboard tests that run in CI on every push.

Accessibility practices demonstrated

  • Every color token pairing meets 4.5:1 for text and 3:1 for UI boundaries, in light and dark themes.
  • Status is never conveyed by color alone: badges carry text, and the current nav item and step have shape indicators.
  • Layouts reflow to 320px wide without horizontal scrolling (1.4.10), and text spacing can be overridden (1.4.12).

  • Skip link, logical heading structure and labelled landmarks on every page.
  • A two-tone focus indicator that stays visible on any background and in Windows High Contrast (forced colors).
  • Full keyboard support with roving tabindex for tabs and arrow-key navigation for accordions.
  • Animations are disabled when the user prefers reduced motion.

  • Specific, actionable error messages (“Enter a 10-digit phone number”, not “Invalid input”).
  • Hints are associated with fields through aria-describedby, and inputs are sized to the expected answer.
  • Users can review and change every answer before submitting (3.3.4 Error Prevention).

  • Native elements first (<button>, <dialog>, <fieldset>); ARIA is added only where HTML has no equivalent.
  • Dynamic updates use polite live regions (4.1.3 Status Messages).
  • Tested with axe-core in CI, plus manual testing with NVDA, JAWS and keyboard only.
